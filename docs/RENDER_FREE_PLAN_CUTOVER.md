# Render Free Plan Cutover Runbook

**Prerequisite:** the pull request that moves email to Resend is open and reviewed.

- [ ] 1. **Resend account.** Free tier: 100 emails/day, 3,000/month, 1 verified domain — far above a single-department pilot; watch it as more departments onboard. Verify `elogbookgothos.in` by adding the SPF/DKIM DNS records Resend gives; the sender becomes something like `noreply@elogbookgothos.in`. Generate an API key. **Do not paste the key into any session, prompt, file or commit (§10)** — a key in a chat log is burned. Mail will not send until the domain verifies.
- [ ] 2. **Add `RESEND_API_KEY` and `EMAIL_FROM` to the Render service's environment BEFORE merging.** The old code ignores them, so this is safe. Leave `EMAIL_USER` and `EMAIL_APP_PASSWORD` in place until the cutover is verified, so reverting the PR on the paid plan restores Gmail.
- [ ] 3. **Merge the PR** and wait for Render's deploy.
- [ ] 4. **On the paid plan, trigger one real send per sender path:** registration OTP, password reset, account-created, HOD approval request. This is the **point of no return** — once Free is active SMTP is gone and the old path cannot be tested. Record per send: the flow, the timestamp, the Resend dashboard status (delivered), and the Render log lines for that moment. **Do not record OTPs, passwords or bodies.** Confirm the Render logs show no OTP, password, or recipient detail. "Email works" without all four is not evidence.
- [ ] 5. **Change the plan.** Render dashboard → the service → Compute → Edit → select Free → save. Plan changes take effect on the first successful deploy afterward. **First confirm the Free option actually appears** — Render's docs describe upgrading but never explicitly confirm downgrading. If Free is not offered, **stop and re-plan**: creating a fresh service would change the URL, which drags in a frontend rebuild and an `ALLOWED_ORIGINS` change.
- [ ] 6. **Check the workspace.** Open the Render workspace and confirm whether the ELogBook API is the only Free *web service* (the Redis does not count). This decides the pinger schedule below.
- [ ] 7. **Set up the pinger.** cron-job.org (supports raw cron and the `Asia/Kolkata` timezone) or UptimeRobot, hitting `https://elogbook-api.onrender.com/api/healthz`. That route returns `{"status":"ok"}` with no database access, so it wakes the process without touching Neon.
- [ ] 8. **Post-cutover checks:** `curl https://elogbook-api.onrender.com/api/healthz` returns `200 {"status":"ok"}`; complete one real password reset end to end from the deployed frontend; check the pinger's run history the next morning; check Render's instance-hours usage after a few days against the projection below.
- [ ] 9. **Standing rules:** no second Free web service in this workspace; glance at the usage page monthly.

**Pinger schedule — how the 750 hours work** (from Render's docs while planning; confirm on the workspace usage page a few days in, since Render's page is loose about whether Key Value draws on the quota): the hours are pooled per **workspace**, not per service; consumed by Free **web services** only; spun-down time is free; build minutes and bandwidth are separate allowances. **Exhausting the 750 suspends every Free web service until the 1st of the next month, with no warning and no remedy except the paid plan.** 24 × 31 = **744**, not 750, so a single always-on service fits with ~6 hours spare.
- [ ] **Only Free web service in the workspace → ping 24/7**, `*/10 * * * *` (well inside the 15-minute idle threshold). 744 of 750 hours.
- [ ] **Another Free web service shares the pool → 24/7 is impossible** (two always-on would need 1,488 hours). Either move one to its own workspace, or size a sleep window from the other service's *real* instance-hours. Do not guess the window; read the figure first.
- [ ] **Optional sleep window for margin** (timezone `Asia/Kolkata`; **two** cron entries, since one expression cannot carve half an hour out of a single hour): minutes `*/10` hours `0-2,4-23`; and minutes `30,40,50` hour `3`. The 02:50 → 03:30 gap means the service sleeps ~03:15–03:30, about 25 min/day, ~731 hours in a 31-day month, ~19 spare. Skipping the whole 03:00–04:00 hour (`*/10 0-2,4-23 * * *`) is one expression and ~721 hours. Acceptable consequences: the first request after a window waits ~1 minute; a Razorpay webhook firing inside it may time out but is retried for 24 hours (`payments-webhook.ts:116`).
