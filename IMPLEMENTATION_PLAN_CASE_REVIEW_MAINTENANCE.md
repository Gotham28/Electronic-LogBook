# ELogbook: case review details and maintenance notices — implementation record

Planning baseline: `main` at `4f5c26d7aa3b679247a2e8e1739b8603f81fed1d` (confirmed up to date with `origin/main` on 2026-09-30). This document records the agreed behavior, implementation steps, and the actual validation performed in the workspace. The implementation is present in the working tree and remains uncommitted.

**Scope amendment:** The user later requested removal of the maintenance email feature. Email-related requirements below describe the earlier approved plan and are superseded. The maintenance notice remains in-app only; existing account emails are unaffected.

## Agreed product behavior

1. A professor or HOD reviewing a case sees every field submitted by the resident in the review screen, in a readable layout that does not crowd the queue. The HOD's review queue uses the same faculty review component. In the student's logbook inspector, case rows stay compact and offer expandable full details.
2. The administrator schedules maintenance by entering the start and end times in **IST** and choosing the audience roles. The administrator does not type a title, message, or impact description. The server supplies fixed wording. Scheduling, material updates, and cancellation send real email through the existing Resend integration to approved users in the selected roles.
3. During an **active** maintenance window, a restrained message bubble automatically appears above the bottom-right Arogya icon after each login. No click is needed to read it. It is clearly labelled as an **ELogbook service notice**, with Arogya acting as its presenter rather than claiming the notice was AI-generated. It can be closed. The notice remains accessible through Arogya and the notification bell. Replace the large page banner with this interaction.
4. Maintenance is an announcement, not an access lock. The wording warns of possible brief interruptions and does not promise uninterrupted access. Use IST regardless of the administrator's device timezone. A user already signed in when maintenance becomes active should also see the notice once when the active state is first detected.

## Exact wording

Use one server-owned message builder for the in-app and email variants so dates and claims stay consistent. The dates below are variable; no administrator-entered text is included.

- **Scheduled email subject:** `ELogbook scheduled maintenance`
- **Scheduled email body:** `Hello,\n\nELogbook is scheduled for maintenance from {start IST} to {end IST}. Please save your work beforehand, as you may experience brief interruptions during this time.\n\nThank you for your understanding.\nThe ELogbook Team`
- **Active bubble:** heading `ELogbook service notice`; body `ELogbook maintenance is in progress until {end IST}. Please save your work regularly; you may experience brief interruptions. Thank you for your understanding.`
- **Updated email:** heading `ELogbook maintenance schedule updated`; say the window is now `{start IST} to {end IST}`, followed by the same save-work and thank-you sentences.
- **Cancelled email:** heading `ELogbook maintenance cancelled`; say the maintenance previously scheduled for `{start IST} to {end IST}` has been cancelled, followed by `Thank you for your understanding.`

Use matching short scheduled and active text in the notification bell and Arogya panel. Keep the copy plain and professional: no typing animation, sound, confetti, simulated conversation, or claim that Arogya generated the notice.

## Implementation task 1: full case details for reviewers

2. In `artifacts/mockup-sandbox/src/components/ProfessorPortal.tsx`, give case queue items a specific TypeScript shape for those fields instead of relying on unchecked `any` access. Group content as patient/context; complaints and history; examination and investigations; diagnoses; management and outcome; learning points. Show every submitted value without truncation, preserve paragraphs and line breaks, and show `Not recorded` for an empty optional field. Keep the current evaluation controls beside the details on wide screens and below them on narrow screens.
3. In the **View Logbook → Clinical Case Logs** table in the same component, retain concise summary rows. Add an accessible `View details`/`Hide details` control per row and reuse the case detail component in an expanded row or drawer. Include faculty remarks and review status in this historical view when present. Do not turn the entire row into a hard-to-discover click target. Keep the existing category filter and error state.
4. Preserve demo-mode UHID hiding. The authorized reviewer still sees the real UHID outside demo mode; do not log case text, UHID, or response bodies. Do not add a new case endpoint or broaden the existing professor/HOD access rules. Keep `studentsTable.id` for the student route and `usersTable.id` for reviewer IDs.
5. Add focused API tests in `artifacts/api-server/tests/` using the existing in-process test database: submit a synthetic case with distinct values in every field; assert each one arrives in the assigned professor's queue and the HOD's own assigned queue; assert the case is absent from another professor's and another department's queue. Record individual status/body evidence for unauthenticated, authorized, wrong reviewer/department, and nonexistent targets. The existing queue intentionally returns `403` for nonexistent faculty IDs to avoid enumeration; do not change that behavior to satisfy a generic test expectation.
6. Manually review desktop and mobile layouts with a long multiline case, missing optional fields, demo mode, and navigation between cases. Confirm verification and rejection still target the selected case and have no change in behavior.

**Acceptance:** A reviewer can read all submitted fields before acting; an unauthorized reviewer receives none of those fields; historical case details are reachable without expanding every case at once; procedure and academic review displays are unchanged.

## Implementation task 2: fixed maintenance notices, dates, Arogya bubble, and email

Implement after task 1 is reviewed. Keep this as its own diff. A versioned migration is required: although the table exists in the Drizzle schema, the project's hand-maintained migration runner currently omits it. Add the table to that runner through a new idempotent migration; do not apply it to a live database.

1. Create a small server-side maintenance-message helper in `artifacts/api-server/src/lib/`. It formats `startAt` and `endAt` in `Asia/Kolkata` and supplies fixed scheduled, active, updated, and cancelled text. Keep one source of truth for date formatting and wording; have `GET /api/announcements/current` return the rendered notice text alongside timestamps/status so browser surfaces do not invent their own copy. Render email HTML with the existing `escapeHtml`/`wrapEmail` helpers in `mailer.ts`. No AI call participates in this path.
2. In `artifacts/mockup-sandbox/src/components/MaintenanceAnnouncements.tsx`, remove title, description, expected-impact, and `Send email notification now` inputs. Keep audience-role selection and start/end controls, label both as IST, preview the exact fixed text with selected times, and show a visible load error instead of an empty-table state when the fetch fails. Disable Save for invalid or reversed times and show the server's validation error if it rejects the request.
3. Convert a `datetime-local` value explicitly from IST to a UTC ISO string before POST/PATCH; do not rely on the browser timezone. For edit, format stored ISO values back into IST input values with `Intl.DateTimeFormat(..., { timeZone: 'Asia/Kolkata' })` or an equivalent tested conversion. Test a machine set to IST and one set to another timezone. New schedules require a future start and `endAt > startAt`; for an active announcement, preserve its original start and allow a future end-time correction. Reject edits to completed/cancelled announcements. Keep timestamps as `timestamptz` in storage.
4. In `artifacts/api-server/src/routes/superadmin.ts`, ignore legacy client-supplied `title`, `description`, `expectedImpact`, and `sendEmail` values while accepting the old request shape during a cached-client transition; never persist or echo that free text as the new notice. Store fixed title/description. Derive email content on the server from timestamps and event type. Send the scheduled notice automatically after create, an updated notice when the time/audience changes, and a cancellation notice on cancel. For an audience change, send the update to the new audience and a cancellation/removal notice to roles removed from the audience so previously notified users are not left with stale instructions. Keep the admin-only route guard. Return a truthful delivery summary to the admin; saving the schedule must never be reported as an email success if Resend failed.
5. Implement `sendAnnouncementEmails` in `artifacts/api-server/src/lib/mailer.ts` using the existing Resend API settings. Query approved `usersTable` accounts whose role is in the announcement audience, deduplicate addresses, and send one email per recipient with bounded concurrency. Do not include recipient lists in the email body. Use a text part and escaped HTML part. Keep logs to announcement ID, event, accepted count, failed count, and status code; never log addresses, provider response bodies, credentials, or user-entered clinical data. Treat provider acceptance as **accepted for delivery**, not proof that the recipient read the email. Surface partial failures in the admin UI. Do not auto-retry blindly, which could duplicate notices; a durable retry system can be a later task if needed.
6. Remove the 24-hour and 1-hour send side effects from `GET /api/announcements/current` in `artifacts/api-server/src/routes/announcements.ts`. A read request should return announcements only. Existing reminder flags can remain unused; no schema alteration is required. Do not claim scheduled reminder emails are included in this fix.
7. In `artifacts/mockup-sandbox/src/components/layout/AppLayout.tsx`, replace `MaintenanceBanner` with a compact Arogya-anchored notice bubble. Fetch current announcements after login and refresh them at a modest interval while the app is open so an active transition or cancellation is noticed. Only active, non-cancelled announcements for the user's role trigger the automatic bubble. Use an announcement ID plus current login session key to show it once per login, including a user already online when maintenance starts. Dismissing the bubble does not remove the notice from the bell or Arogya panel. Show the bubble after a required legal disclaimer closes: expose an acceptance callback from `LegalDisclaimerModal.tsx` to `AppLayout.tsx`, and determine its initial accepted state before showing the bubble. 8. In `artifacts/mockup-sandbox/src/components/arogya/ArogyaPanel.tsx`, display maintenance as a pinned, labelled `ELogbook service notice` supplied by the announcement API. It should look like an official status card within Arogya, not a fabricated AI chat answer. Keep it visible after the automatic bubble is dismissed. Maintain the notification bell item with the same fixed wording. On fetch failure, show an appropriate visible error for the notice surface; never fabricate an empty or inactive state as if the server confirmed one.
9. In `artifacts/mockup-sandbox/src/components/LoginPage.tsx` and `src/lib/session.ts`, reset the maintenance-bubble session marker on successful login/sign-out. ## Scope and deployment notes

- These are two features and should be implemented and reviewed as separate changes. Start the second only after the first is verified. Do not bundle unrelated cleanup or modify other clinical log types.
- No live database queries, migrations, `drizzle-kit push`, or external email sends are needed to implement or test this plan. Use the in-process PGlite tests and intercepted provider calls. - Email delivery will depend on provider acceptance and configured credentials. This plan does not promise guaranteed delivery or timed reminder emails. If the pilot's audience size makes synchronous sending slow, review a durable queue as a separate change rather than silently dropping recipients.
- Existing custom maintenance records can be displayed using the fixed wording derived from their dates; do not copy their old free-text description into new notices or emails. Test this compatibility before deployment.
